# Tsugi プロダクト評価 — 長所・短所・改善案（ASSESSMENT）

`docs/FEATURE-AUDIT.md` が「機能の過不足」台帳であるのに対し、本書はプロダクト・
プロセス・運用まで含めた評価。2026-08 時点の実状（verify 190/190・CPU 23 スイート
PASS・ruff clean）に基づき、観測した事実のみを根拠にする。
改善案の表がそのまま `INSTRUCTIONS-OPUS.md` / `INSTRUCTIONS-SONNET.md` の
バックログになる（単一情報源）。

## 長所

1. **fail-safe 設計の一貫性**: 偽OK ≫ 偽BLOCK の非対称コストを全 13 検証層が共有。
   点推定→Wilson 上側限界 5 箇所・DAG マージの保守側選択（`correlated=True`）・
   検出不能な形は線形フォールバック。方針が文書だけでなくコードの隅々まで貫通している。
2. **検証基盤の厚さと「欠陥→不変条件」文化**: 機械検証可能な不変条件 190 件＋
   27 テストファイル＋property test（10 性質×200 試行）。実際に起きたバージョン
   ドリフトが即座に不変条件 62 として固定された実例あり。回帰が構造的に起きにくい。
3. **誠実な主張**: GPU 未検証を run.py の SUMMARY で毎回明示。「静的 cond=1 は下界」
   「scale=1 仮定」等をレポート出力に明記する「暗黙化しない」慣例。過大広告がない。
4. **引き継ぎ可能性**: FEATURE-AUDIT.md / SOCRATIC-50 が前提知識ゼロの読者を想定し、
   実際にセッション再開がこの 2 文書だけで成立した。
5. **台帳駆動の自己改善プロセス**: facade 未接続 11 件を系統スキャンで発見→全接続→
   スキャン自体を CI 化（不変条件 57）。プロセスが再現可能。
6. **判定が機械可読**: `Audit.to_dict()`（JSON 直列化可能）と終了コード契約
   （OK/INFO=0・WARN=1・BLOCK=2）を持ち、CI が判定をそのままゲートに使える
   （散文パースが不要）。First Principles 分析で発見した不足を解消済み（不変条件 69）。

## 短所

1. **製品価値の中核が「実行」だけ未達**: codegen は実装され（A-4・L2）、単一 IR から
   実 PTX/実 AMDGCN が出てベンダーのアセンブラが受理する。残るのは**生成物の実行**
   （L3）と GPU 実機検証（A-2）。「単一ソースで両ベンダー」は*生成レベルでは実績*に
   なったが、*数値レベルでは依然として約束*である。
2. **検証器自身の実機校正が未了（手続きは完成）**: SAFETY=4.0 は依然 CPU
   シミュレーション内の経験値。ただし「実機の run が手に入った瞬間に機械的に校正する
   手続き」は完成し実機入口に接続済み（`calibration.calibrate_safety`・
   `docs/GPU-BRINGUP.md`）。残るのは実機そのもので、検証器側の設計課題ではなくなった。
3. **想定入口（torch.compile）— 機械語まで届いた。残りは実行時層のみ**: PyTorch 開発者は
   `tsugi.verify(fx_graph)` でゲート付き判定（不変条件 89）に加え、**codegen 検証**まで
   受け取る（FX → IR 降下・不変条件 98）。降下の意味論は torch eager と照合済み。
   残るのは worstcase/attribution/タスク別 decision で、これらは**実行時出力**が要るため
   L3（実機）待ち——検証器側の設計課題ではなくなった（A-3 残）。
   なお第 60 回はこの経路で **実 FX に対する全面的な偽OK**（実モデルが必ず「発散 0」と
   報告される）を発見・修正した。duck-typed stand-in だけの検証には限界がある。
4. **リポジトリ運用の未成熟（ゲート側は整備済み）**: main ブランチ無し・タグ/Release ゼロ・
   Actions 実質無効（権限制約）。ただしゲート自体は `python check.py` の **単一定義** に畳まれ、
   ローカル/CI/リリースが同じものを呼ぶ（不変条件 88 がゲートの再列挙を禁じドリフトを構造的に
   防ぐ）。Actions を有効化する日は `python check.py` を呼ぶだけで CI とローカルが一致する。
5. **verify.py の成長限界**: 1,400 行超・実行数十秒。テーマ別 12 関数に分割済みだが
   単一ファイルの限界は近い。
6. **ドキュメント肥大**: docs 29 本。README に目的別の reading path を新設して導線は
   確保したが（「使う人／仕組み／引き継ぐ人／その他」）、文書数自体は多いまま。

## プロダクト完成の線引き（First Principles・"完成"を less dumb に定義）

「このプロダクトを完成させる」を素朴に取ると「codegen（PTX/AMDGCN 生成）と実機 GPU を
実装する」だが、それはこの環境では原理的に不可能（LLVM/MLIR・実機なし）。要件を
less dumb に定義し直す:

**Tsugi は 2 つのプロダクトの合成である**:
1. **クロスベンダー移植性検証器**（今日出荷できる・CPU 完結・GPU 不要）
2. **単一ソース codegen コンパイラ**（L2 まで完成・CPU 完結。L3=実行のみ実機待ち）

> **2026-08 追記（前提が反転した）**: 上の「(2) はこの環境では原理的に不可能」は
> **要件の誤り**だった。生成は純関数、アセンブルは CPU ツール、実機が要るのは
> *実行だけ*である。第 59 回でこの誤りを正し、codegen は L2 まで到達した。
> 以下の (2) に関する記述はこの追記を前提に読むこと。
>
> **どこまで第三者のツールが真値になっているか**（すべて CPU・GPU 不要）:
>
> | 段 | 何を確かめるか | 真値 |
> |---|---|---|
> | ① 受理 | 命令の存在・構文・arch 可用性 | ptxas / llvm-mc |
> | ② 符号化 | 意図した命令が実際にその機械語になったか | llvm-objdump / llvm-nm |
> | ③ ロード構造 | ローダが要求する部品（記述子・メタデータ）の実在 | ELF（readelf/nm/objdump） |
> | ④ 命令選択 | その命令を選んだ判断が妥当か | **LLVM の AMDGPU/NVPTX バックエンド** |
> | ⑤ 実行 | 数値・レイアウト・性能 | **実機（未到達・L3）** |
>
> ②③④はいずれも**実際に欠陥を見つけた**（RDNA3 の別名綴り／`.amdhsa_accum_offset` の
> arch 依存／`add.f32` の FMA contraction）。検査が飾りでない証拠になっている。

(1) は**完成し、使える**: `pip install -e python/ && python -m tsugi` で移植ブロッカーを
実機前に告げ、終了コードが CI ゲート契約（BLOCK=2）に忠実。13 検証層＋メタ層が
190 不変条件で機械検証され、値の taxonomy（数値等価/起動可能/タスク影響/精度ポリシー）は
文献に紐付く。**(1) の「完成」の判断基準は「新規ユーザーが 1 コマンドで移植判定を得られ、
その判定が正しい」——これは満たされた**（第 55 回で摩擦とプロセス層偽OK を除去）。

(2) は **L2 まで解凍された**（`python/tsugi/codegen.py`・`docs/CODEGEN.md`）。
単一 IR → 3 ターゲットの実アセンブリ → ベンダーのアセンブラが受理、までが CPU で
機械検証される。実機が要るのは L3（実行・レイアウト接合・数値照合）だけで、その
手順は `docs/GPU-BRINGUP.md` と `audit_cross_vendor` に凍結済み。

**delete（第 2 段階）の適用**: 数値発散モデルの taxonomy（入力精度/累積順序/丸めモード＋
tf32x3 緩和）はクロスベンダーの主要発散源を網羅し、これ以上の微細モデルは限界効用が薄い。
検証層は各々が実発散クラスを捕まえテスト済みゆえ削除は価値破壊（"add back 10%" 則の逆）。
→ **今後は数値モデルの追加でなく、(1) の実運用価値（使いやすさ・正しさ・正直な境界）の
維持と、(2) の実機着手を完成軸とする**。

**完成の判定基準（すべて実測で満たした）**:

| 基準 | 実証 |
|---|---|
| 新規ユーザーが 1 コマンドで移植判定を得る | `python -m tsugi` → レポート＋exit 2 |
| プログラムから 1 コールで使える | `tsugi.verify("k.py")` → `Audit` |
| **配布物**がソースツリー無しで動く | wheel をクリーン venv に入れ `python -m tsugi` が exit 2 |
| 判定が CI ゲート契約に忠実 | OK/INFO=0・WARN=1・**BLOCK=2**（不変条件 86） |
| 開発ゲートが 1 コマンド・単一定義 | `python check.py`（17〜18s・不変条件 88） |
| 主張が実装と一致（過大広告なし） | README が ✅ 今日動く / 🔜 Phase 4 を分離 |
| **想定ユーザー（PyTorch 開発者）が同じ 1 コールで使える** | `tsugi.verify(fx_graph)` → ゲート付き `Audit`（不変条件 89） |
| **想定ユーザーのモデルが実機械語まで到達する** | FX → IR → PTX/AMDGCN（不変条件 98）・意味論は torch eager と照合（不変条件 100） |
| **実機テンソルをそのまま渡せる** | テンソルを取る公開関数を面で掃いて device 対応（不変条件 105） |
| ドキュメントの API 参照が腐らない | docs/README の python 例を AST で実在検査（不変条件 104） |
| **単一ソースが両ベンダーの実機械語まで到達する** | 1 IR → PTX/AMDGCN → アセンブル・符号化照合・ロード構造・LLVM との命令選択照合（不変条件 90-97） |

> 完成の一言: **検証器プロダクトは完成し、codegen も CPU で到達しうる限界まで到達した**。
> 単一ソースが両ベンダーの実機械語になり、その正しさをベンダー自身のツール・LLVM・
> torch eager が裏づける。**想定ユーザー（PyTorch 開発者）も同じものを受け取る**。
> 残るのは **実機でしか判らないこと**——生成物を走らせたときの数値・レイアウト接合・
> 性能（L3）だけであり、これは「codegen は不可能」という過去の誤りと違って *実際に
> 検証不能*である（レイアウト接合には独立オラクルが存在しない: LLVM も行列コアの
> フラグメント配置を教えてくれない。実機出力と突き合わせる以外に方法がない）。
>
> 構造 op（chunk/cat/index）を降下できないのも同じ根から来る**設計上の境界**であり、
> 実装漏れではない: 計算済みの値をスライスするにはレーンと要素の対応を IR が知る必要が
> あり、それはレイアウトの問題そのもの。実機なしに決め打てば偽OK になる。
>
> **第 59-60 回で学んだこと**: 完成の判定を *実装者の視点* で下すと穴が残る。
> 「codegen は不可能」も「残るは L3 だけ」も、想定ユーザーの経路を歩けば偽と判った。
> 実 torch を入れた途端に **実モデルが必ず「発散 0」と報告される**偽OK が出たのも、
> duck-typed stand-in だけで満足していたから。*使う人が最初に打つコマンド*を、
> *本物の依存関係*で通すこと——これが完成判定の最低条件である。
