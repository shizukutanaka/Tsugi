# Tsugi プロダクト評価 — 長所・短所・改善案（ASSESSMENT）

`docs/FEATURE-AUDIT.md` が「機能の過不足」台帳であるのに対し、本書はプロダクト・
プロセス・運用まで含めた評価。**観測した事実のみ**を根拠にし、実測値は
`python check.py` の出力を参照する（数値を文章に焼き込むと腐る——第 61 回に
6 件すべて腐っているのを発見した。CPU スイート数だけは不変条件 107 が機械照合する）。
改善案の表がそのまま `INSTRUCTIONS-OPUS.md` / `INSTRUCTIONS-SONNET.md` の
バックログになる（単一情報源）。

## 長所

1. **fail-safe 設計の一貫性**: 偽OK ≫ 偽BLOCK の非対称コストを**全検証層**が共有。
   点推定→Wilson 上側限界 5 箇所・DAG マージの保守側選択（`correlated=True`）・
   検出不能な形は線形フォールバック。方針が文書だけでなくコードの隅々まで貫通している。
2. **検証基盤の厚さと「欠陥→不変条件」文化**: 機械検証可能な不変条件＋全 CPU スイート
   ＋property test（10 性質×200 試行）。実際に起きたバージョンドリフトが即座に
   不変条件 62 として固定された実例あり。回帰が構造的に起きにくい。
   **ただし限界がある**——厚みは *検査の階層を 1 段見落とす* ことを防がない（短所 7）。
3. **誠実な主張**: GPU 未検証を run.py の SUMMARY で毎回明示。「静的 cond=1 は下界」
   「scale=1 仮定」等をレポート出力に明記する「暗黙化しない」慣例。過大広告がない。
4. **引き継ぎ可能性**: FEATURE-AUDIT.md / SOCRATIC-50 が前提知識ゼロの読者を想定し、
   実際にセッション再開がこの 2 文書だけで成立した。
5. **台帳駆動の自己改善プロセス**: facade 未接続 11 件を系統スキャンで発見→全接続→
   スキャン自体を CI 化（不変条件 57）。プロセスが再現可能。
6. **判定が機械可読**: `Audit.to_dict()`（JSON 直列化可能）と終了コード契約
   （OK/INFO=0・WARN=1・BLOCK=2）を持ち、CI が判定をそのままゲートに使える
   （散文パースが不要）。First Principles 分析で発見した不足を解消済み（不変条件 69）。
7. **真値が自分でなく第三者のツールである（第 59-60 回で獲得）**: codegen の正しさを
   自分で主張せず、**5 段すべてを外部に問う**——①ptxas/llvm-mc が受理するか
   ②llvm-objdump が意図した命令を復号するか ③ELF にローダの部品があるか
   ④LLVM のバックエンドが同じ命令を選ぶか ⑤torch eager と数値が一致するか。
   ②③④⑤はいずれも**実際に欠陥を見つけた**（RDNA3 の別名綴り・記述子の arch 依存・
   `add.f32` の FMA contraction・eps 欠落/gelu 置換/転置落ち/bias 落ち）。
8. **意味論が保存されていることの実証**: `interp.evaluate`（IR の NumPy 意味論）で
   「PyTorch モデル → FX → Tsugi IR → 評価」が torch eager と一致する
   （重み込み MLP まで max|Δ| < 1e-9）。アセンブラにも LLVM にも問えない層を埋めた。
9. **想定ユーザーの経路を本物の依存で通す規律**: `torch.compile(backend="tsugi")` を
   実 torch で走らせ、GPU テンソルを公開 API 全面で受け、docs の API 参照を AST 検査
   （不変条件 101/104/105）。第 60 回はこの規律で **実モデルが必ず「発散 0」と報告される**
   全面的な偽OK を発見した。
10. **判定が「天井」でなく「実測」に立つ（第 62 回で獲得）**: 降下 IR に実行可能な
    意味があるので、`dot` の意味論をベンダー模倣に差し替えるだけで**同じ IR を 2 ベンダー
    として CPU で走らせられる**（`tsugi_torch.simulate`）。既知 4 クラス（累積順序・
    f16 累積・TF32 入力・RTZ 丸め）ごとに発散とフリップ率を実測し、BLOCK の根拠を
    静的天井から実測へ移した。新しい数値定数は 1 つも導入していない（既存の
    `simulate_vendor_matmul` / `decision_flips` / `flip_rate_upper_bound` の合成）。

## 短所

1. **製品価値の中核が「実行」だけ未達**: codegen は実装され（A-4・L2）、単一 IR から
   実 PTX/実 AMDGCN が出てベンダーのアセンブラが受理する。残るのは**生成物の実行**
   （L3）と GPU 実機検証（A-2）。「単一ソースで両ベンダー」は*生成レベルでは実績*に
   なったが、*数値レベルでは依然として約束*である。
2. **検証器自身の実機校正が未了（手続きは完成）**: SAFETY=4.0 は依然 CPU
   シミュレーション内の経験値。ただし「実機の run が手に入った瞬間に機械的に校正する
   手続き」は完成し実機入口に接続済み（`calibration.calibrate_safety`・
   `docs/GPU-BRINGUP.md`）。残るのは実機そのもので、検証器側の設計課題ではなくなった。
3. **想定入口（torch.compile）— 機械語まで届いた。残りは実行時層のみ**: PyTorch 開発者は
   `tsugi.verify(fx_graph)` でゲート付き判定（不変条件 89）に加え、**codegen 検証**まで
   受け取る（FX → IR 降下・不変条件 98）。降下の意味論は torch eager と照合済み。
   残るのは worstcase/attribution/タスク別 decision で、これらは**実行時出力**が要るため
   L3（実機）待ち——検証器側の設計課題ではなくなった（A-3 残）。
   なお第 60 回はこの経路で **実 FX に対する全面的な偽OK**（実モデルが必ず「発散 0」と
   報告される）を発見・修正した。duck-typed stand-in だけの検証には限界がある。
4. **リポジトリ運用の未成熟（ゲート側は整備済み）**: main ブランチ無し・タグ/Release ゼロ・
   Actions 実質無効（権限制約）。ただしゲート自体は `python check.py` の **単一定義** に畳まれ、
   ローカル/CI/リリースが同じものを呼ぶ（不変条件 88 がゲートの再列挙を禁じドリフトを構造的に
   防ぐ）。Actions を有効化する日は `python check.py` を呼ぶだけで CI とローカルが一致する。
5. **verify.py の成長限界を超えた**: 第 58 回時点の「1,400 行超・限界は近い」は
   **既に限界を越えている**（現在その倍近い）。テーマ別 12 関数に内部分割済みなので
   可読性はまだ保たれており、**今の分割は churn が利益を上回る**——よって
   *発火条件つき* の改善案として記録する（下表）。「今要らない部品を作らない」。
6. **ドキュメント肥大**: README に目的別の reading path があるが文書数自体は多い。
   さらに **文書の数値主張は腐る**——第 61 回に 6 件すべて（不変条件件数・スイート数・
   モジュール数・docs 本数・行数・ゲート秒数）が実態とずれているのを発見した。
   対処: 数えられる数値は文章から削り、CPU スイート数だけ不変条件 107 で機械照合する。
7. **検査の階層を 1 段見落としていた（本ラウンド最大の発見）**: ゲートが
   ディスク上のスイートのうち **4 本を一度も実行していなかった**
   （attribution=新視点12・blame=新視点13・worstcase・torch.compile backend）。
   `_orphan_tests()` は「各 test_* 関数が *そのファイルの* main() に登録されているか」
   しか見ておらず、「*そのファイル自体が* run.py のスイート表に載っているか」を
   問うていなかった。4 本とも単体では PASS するので**腐っていたのではなくゲート外**
   だった。→ 対処済み（全スイート登録＋`_orphan_tests()` をファイル単位へ拡張・
   不変条件 106）。**教訓: 不変条件の *数* は検査の *深さ* を保証しない。**
8. **同じ穴が製品側にもあった（同ラウンドで発見・修正）**: 全検証層を掲げながら
   `python -m tsugi k.py` の既定出力に現れるのは 5 層で、残りは *データが無いので
   走っていない*。レポートはその不在を告げず、利用者は「移植可」を **全層を通した判定**
   と読む。→ `LAYER_CATALOG` を持ち、**走らなかった層を名指しし、何を渡せば走るかまで
   書く**ようにした（不変条件 108・3 入口すべてに適用）。開発ゲートの「緑は何を意味
   するか」と同じ規律を製品出力にも適用したもの。なお同ラウンドで、文書 7 箇所が
   「13 検証層」と書いているのに実体は 15 層という食い違いも見つかった——数え方の
   異なる分類が並存していた。**層数は `audit.LAYER_CATALOG` が単一情報源**とし、
   散文からは数を消した（Q63 の原則の適用）。
9. **偽BLOCK の常態化という盲点（第 62 回・修正済）**: 「偽OK ≫ 偽BLOCK」を 61 回
   掲げてきたが、その**裏側**を一度も点検していなかった。楔ユーザーが受け取る唯一の
   数値（静的 `model_divergence` とそこから導いた flip 上界）は実測の **200〜1700 倍**
   で、どのモデルでも「フリップ率 ≤ 24〜66%」としか出ない——モデルを区別しないので
   情報量ゼロ、しかも既定予算を必ず超える＝**常に BLOCK**。真な上界ではあるが
   **無情報**であり、読まれなくなった警告は偽OK と同じく判定を殺す。乖離の原因は
   構造的で、伝播モデルは格納 dtype `u(fp16)` を発散単位にするが、両ベンダーが f32 で
   累積するなら差は `u(f32)` スケール（2¹³ 倍小さい）。→ 静的値を「許容の天井」と
   名乗らせ、判定は CPU 2 ベンダー模倣の実測へ移した（長所 10・不変条件 110）。
   **教訓: fail-safe は「常に赤」と同義ではない。契約の検査（「間違った BLOCK を
   出さない」）は「意味のある BLOCK を出す」を保証しない。**
10. **静的伝播モデルは校正されていない（天井としてのみ有効）**: 上記の乖離は
    「モデルが間違っている」のではなく「格納 dtype を単位にした上界」なので、天井
    としての役割は残る。ただし *予測* としての再校正には実機のクロスベンダー実測が
    要る（A-2 と同じ実機待ち）。それまでは天井と実測の両方を併記し、**真値はその間**
    としか言えない。模倣も既知クラスだけなので**実機発散の下界**である。
11. **「実測」と称して別のものを測っていた（第 62 回・修正済）**: `torch.compile` 経路で
    代表入力に使っていた `example_inputs[0]` は、dynamo が**重みを引数へ持ち上げる**
    ため `nn.Parameter` だった。A-3 以来「sample 実測: scale=…」は活性でなく重み行列の
    統計を報告していた。**実測と称して別のものを測るのは、静的仮定を残すより悪い**——
    「(cond=1 lower bound)」なら下界だと分かるが、「実測」は活性の測定だと読まれる。
    → 型で活性を選び、束縛は位置対応が取れるときだけ行う（不変条件 111）。
    この欠陥はスタンドインのグラフでは**永久に現れない**（重みが持ち上がらないため）。

## プロダクト完成の線引き（First Principles・"完成"を less dumb に定義）

「このプロダクトを完成させる」を素朴に取ると「codegen（PTX/AMDGCN 生成）と実機 GPU を
実装する」だが、それはこの環境では原理的に不可能（LLVM/MLIR・実機なし）。要件を
less dumb に定義し直す:

**Tsugi は 2 つのプロダクトの合成である**:
1. **クロスベンダー移植性検証器**（今日出荷できる・CPU 完結・GPU 不要）
2. **単一ソース codegen コンパイラ**（L2 まで完成・CPU 完結。L3=実行のみ実機待ち）

> **2026-08 追記（前提が反転した）**: 上の「(2) はこの環境では原理的に不可能」は
> **要件の誤り**だった。生成は純関数、アセンブルは CPU ツール、実機が要るのは
> *実行だけ*である。第 59 回でこの誤りを正し、codegen は L2 まで到達した。
> 以下の (2) に関する記述はこの追記を前提に読むこと。
>
> **どこまで第三者のツールが真値になっているか**（すべて CPU・GPU 不要）:
>
> | 段 | 何を確かめるか | 真値 |
> |---|---|---|
> | ① 受理 | 命令の存在・構文・arch 可用性 | ptxas / llvm-mc |
> | ② 符号化 | 意図した命令が実際にその機械語になったか | llvm-objdump / llvm-nm |
> | ③ ロード構造 | ローダが要求する部品（記述子・メタデータ）の実在 | ELF（readelf/nm/objdump） |
> | ④ 命令選択 | その命令を選んだ判断が妥当か | **LLVM の AMDGPU/NVPTX バックエンド** |
> | ⑤ 実行 | 数値・レイアウト・性能 | **実機（未到達・L3）** |
>
> ②③④はいずれも**実際に欠陥を見つけた**（RDNA3 の別名綴り／`.amdhsa_accum_offset` の
> arch 依存／`add.f32` の FMA contraction）。検査が飾りでない証拠になっている。

(1) は**完成し、使える**: `pip install -e python/ && python -m tsugi` で移植ブロッカーを
実機前に告げ、終了コードが CI ゲート契約（BLOCK=2）に忠実。全検証層＋メタ層が
`verify.py` の不変条件で機械検証され、値の taxonomy（数値等価/起動可能/タスク影響/精度ポリシー）は
文献に紐付く。**(1) の「完成」の判断基準は「新規ユーザーが 1 コマンドで移植判定を得られ、
その判定が正しい」——これは満たされた**（第 55 回で摩擦とプロセス層偽OK を除去）。

(2) は **L2 まで解凍された**（`python/tsugi/codegen.py`・`docs/CODEGEN.md`）。
単一 IR → 3 ターゲットの実アセンブリ → ベンダーのアセンブラが受理、までが CPU で
機械検証される。実機が要るのは L3（実行・レイアウト接合・数値照合）だけで、その
手順は `docs/GPU-BRINGUP.md` と `audit_cross_vendor` に凍結済み。

**delete（第 2 段階）の適用**: 数値発散モデルの taxonomy（入力精度/累積順序/丸めモード＋
tf32x3 緩和）はクロスベンダーの主要発散源を網羅し、これ以上の微細モデルは限界効用が薄い。
検証層は各々が実発散クラスを捕まえテスト済みゆえ削除は価値破壊（"add back 10%" 則の逆）。
→ **今後は数値モデルの追加でなく、(1) の実運用価値（使いやすさ・正しさ・正直な境界）の
維持と、(2) の実機着手を完成軸とする**。

**完成の判定基準（すべて実測で満たした）**:

| 基準 | 実証 |
|---|---|
| 新規ユーザーが 1 コマンドで移植判定を得る | `python -m tsugi` → レポート＋exit 2 |
| プログラムから 1 コールで使える | `tsugi.verify("k.py")` → `Audit` |
| **配布物**がソースツリー無しで動く | wheel をクリーン venv に入れ `python -m tsugi` が exit 2 |
| 判定が CI ゲート契約に忠実 | OK/INFO=0・WARN=1・**BLOCK=2**（不変条件 86） |
| 開発ゲートが 1 コマンド・単一定義 | `python check.py`（所要は毎回実測を印字・不変条件 88） |
| 主張が実装と一致（過大広告なし） | README が ✅ 今日動く / 🔜 Phase 4 を分離 |
| **想定ユーザー（PyTorch 開発者）が同じ 1 コールで使える** | `tsugi.verify(fx_graph)` → ゲート付き `Audit`（不変条件 89） |
| **想定ユーザーのモデルが実機械語まで到達する** | FX → IR → PTX/AMDGCN（不変条件 98）・意味論は torch eager と照合（不変条件 100） |
| **実機テンソルをそのまま渡せる** | テンソルを取る公開関数を面で掃いて device 対応（不変条件 105） |
| ドキュメントの API 参照が腐らない | docs/README の python 例を AST で実在検査（不変条件 104） |
| **ゲートがディスク上の全スイートを走らせる** | 未登録 0 件・環境起因 skip を件数で報告（不変条件 106） |
| **判定の被覆範囲が利用者に見える** | 走らなかった層を名指し＋必要データを明示（不変条件 108） |
| **単一ソースが両ベンダーの実機械語まで到達する** | 1 IR → PTX/AMDGCN → アセンブル・符号化照合・ロード構造・LLVM との命令選択照合（不変条件 90-97） |
| **判定が天井でなく実測に立つ** | 同じ IR を CPU で 2 ベンダーとして実行し発散とフリップを実測・BLOCK は実測点推定から（不変条件 110） |

> 完成の一言: **検証器プロダクトは完成し、codegen も CPU で到達しうる限界まで到達した**。
> 単一ソースが両ベンダーの実機械語になり、その正しさをベンダー自身のツール・LLVM・
> torch eager が裏づける。**想定ユーザー（PyTorch 開発者）も同じものを受け取る**。
> 残るのは **実機でしか判らないこと**——生成物を走らせたときの数値・レイアウト接合・
> 性能（L3）だけであり、これは「codegen は不可能」という過去の誤りと違って *実際に
> 検証不能*である（レイアウト接合には独立オラクルが存在しない: LLVM も行列コアの
> フラグメント配置を教えてくれない。実機出力と突き合わせる以外に方法がない）。
>
> 構造 op（chunk/cat/index）を降下できないのも同じ根から来る**設計上の境界**であり、
> 実装漏れではない: 計算済みの値をスライスするにはレーンと要素の対応を IR が知る必要が
> あり、それはレイアウトの問題そのもの。実機なしに決め打てば偽OK になる。
>
> **第 59-60 回で学んだこと**: 完成の判定を *実装者の視点* で下すと穴が残る。
> 「codegen は不可能」も「残るは L3 だけ」も、想定ユーザーの経路を歩けば偽と判った。
> 実 torch を入れた途端に **実モデルが必ず「発散 0」と報告される**偽OK が出たのも、
> duck-typed stand-in だけで満足していたから。*使う人が最初に打つコマンド*を、
> *本物の依存関係*で通すこと——これが完成判定の最低条件である。
>
> **第 61 回で学んだこと**: 検証基盤の *厚み*（不変条件 200 件超）は *深さ* を保証
> しない。同じ形の欠陥が 4 段重なっていた——関数→ファイルは見ていたが
> ファイル→ゲートを見ておらず（4 スイートが未実行）、ゲートの被覆は狭めたが
> 製品出力の被覆を狭めておらず（10 層が無言）、入口の 1 つだけ直して他 2 つを
> 忘れ（`audit_runtime` は 15 層中 1 層）、最後に目録自身が層を漏らしていた
> （`torch/FX`）。**「検査を足す」たびに「その検査自身は誰が検査するのか」を
> 一段問う**——これが本ラウンドの規律である。
>
> **第 62 回で学んだこと**: 検査の階層を掘り切ったつもりで、**製品が実際に出す数値**を
> 読んでいなかった。楔ユーザーが受け取る唯一の数字は実測の 200〜1700 倍の *天井* で、
> どのモデルでも「フリップ率 ≤ 24〜66%」としか出ず、既定予算を必ず超えて **常に
> BLOCK** だった。真な上界だが無情報である。61 回にわたり「偽OK ≫ 偽BLOCK」を
> 掲げてきたが、その**裏側**——偽BLOCK が常態化すれば警告は読まれなくなり、偽OK と
> 同じく判定が信号を失う——を一度も点検していなかった。**fail-safe は「常に赤」と
> 同義ではない。** 契約の検査（「間違った BLOCK を出さない」）は「意味のある BLOCK を
> 出す」を保証しない。直し方も同じ規律に従った: 「静的だから天井しか出せない」という
> 前提を疑い（第 1 段階）、降下 IR に既にある実行可能な意味を使って実測へ置き換え、
> 新しい数値定数は 1 つも導入しなかった。**そして「実測へ移す」その作業自体が、
> 測っている対象を取り違えていた 2 つ目の欠陥を露わにした**（代表入力が重み行列
> だった）——結線してみるまで現れない類の欠陥で、スタンドインのグラフでは重みが
> 持ち上がらないため永久に見えなかった。
