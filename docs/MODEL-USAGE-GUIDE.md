# Tsugi 作業のための Claude モデル使い分け表（個人用）

このドキュメントは、このセッションで実際に何が起きたか（どのモデルがどの種類の作業を
行い、何がうまくいった／いかなかったか）を根拠に、Tsugi の開発を続ける際の
モデル・機能の使い分けを 1 人のユーザー向けにまとめたものである。汎用的な
モデル比較ではなく、**この人がこのプロダクトで実際に踏んだパターン**に基づく。

## 前提: このセッションで実際に起きたこと

- ユーザーは `Fable 5` と `Sonnet 5` を `/model` コマンドで繰り返し切り替えていた。
  `Opus`・`Haiku` は本セッションでは一度も使われていない。
- `Fable 5` に切り替えるタイミングは一貫して**戦略的・探索的な指示**の直前だった:
  「このプロダクトの長所短所改善点を洗い出して実行」「ソクラテス式問答法で
  過不足の機能を考える」「市販レベルの品質になるようにする」「使い分け表にまとめて
  実装の最適化」——いずれも「次に何をすべきか」自体をモデルに委ねる、
  オープンエンドな指示。
- `Sonnet 5` に切り替えるタイミングは一貫して**既に方向性が定まった実行**の直前
  だった:「続けて」「Continue from where you left off」——つまり、直前の
  ラウンドと同じパターンをもう一度実行する・承認済みの plan を実装する、という
  スコープの定まった作業。
- `/loop` スキルは一度も使われなかった。だが実際の作業は「同じ種類の改善サイクル
  （facade 未接続バグを探す→直す→テスト→コミット）を 20 回以上、ユーザーが
  毎回手動で『続けて』と再指示する」という形で進んだ——これはまさに `/loop` が
  代替する反復パターンである。
- `Agent`（サブエージェント）は 2 つの文脈で有効に機能した: (1) Qiita/Zenn の
  外部調査（メインの文脈を汚さずに済んだ）、(2) 変更後の `FEATURE-AUDIT.md` の
  正確性を独立した目で再検証する読み取り専用チェック。
- `Workflow`（マルチエージェント orchestration）は一度も呼ばれていない
  （ユーザーが明示的に "workflow" 等のキーワードを使っていないため）。

## 使い分け表

| 作業の種類 | 推奨モデル | 理由（このセッションの実績に基づく） |
|---|---|---|
| **「何を改善すべきか自体」を考えさせる**（例: 長所短所の洗い出し、次の一手の選定） | **Fable 5** | このセッションでユーザー自身が実際にこの使い分けをしていた。オープンエンドな指示（「洗い出して実行」「過不足を考える」）には、次の一手を自律的に選ぶ最上位モデルが理にかなう。実際、Fable 5 起動直後のラウンドで `docs/FEATURE-AUDIT.md`（機能過不足の台帳）の新設や、SSA/DAG 構造の欠落（A-12）のような設計レベルの発見が生まれている。 |
| **承認済み plan の実装・既定パターンの継続**（例: 「続けて」「同じ形式で次のラウンドを」） | **Sonnet 5** | スコープが既に確定した反復作業でこのセッションを通じて安定して機能した（第11〜28回の facade 未接続修正・Wilson 上側限界修正はほぼ全て Sonnet 5 が実施）。Fable 5 ほどのコストをかけずに、確立されたテスト→verify→commit のリズムを崩さず回せる。 |
| **高リスクな正しさの修正**（例: 今回の shape-mismatch silent broadcast のような「偽OK を生みうる」バグ） | **Fable 5**（迷ったらこちら） | このプロジェクトの核心原則は「偽OK が最も致命的」。shape guard の実装では ranking タスクの決定論的ケース・`flip_budget=0.0` の境界テストなど、見落とすと出荷判断を誤らせる非自明な分岐が複数あった。Sonnet 5 でも到達できたが、コストの非対称性（偽OK の代償 ≫ 余分な推論コスト）を踏まえると、この種の変更は最上位モデルを既定にする価値がある。 |
| **単純な定型変換**（バージョン番号の更新・CHANGELOG 見出しの改名・台帳への 1 行追加） | **Haiku**（未使用だが最適） | 本セッションでは実際には Sonnet 5/Fable 5 で行われたが、判断を要さない機械的な書き換えであり、コストに見合わない。今後はこの種の作業を Agent 経由で Haiku に投げるとよい。 |
| **機械的スキャン（関数参照の有無を grep で確認する等）の実行そのもの** | **Haiku**（バックグラウンド Agent） | スキャンを回して結果を出力するだけの工程は判断を要しない。ただし**結果の解釈**（どれが本物の bug で、どれが正当な B-2 除外か）は次の行に該当。 |
| **スキャン結果の解釈・設計判断**（例: どの「facade 未接続」が実装すべき bug で、どれが意図的な非接続か） | **Sonnet 5 以上** | 本セッションで一貫してここに判断力が要った（`bisect_onset` は正当な代替アルゴリズム・`binary_margin` は真の欠陥、という判定は文脈依存の設計判断）。Haiku には荷が重い。 |
| **他モデルが読んで引き継ぐドキュメントの執筆**（例: `FEATURE-AUDIT.md`） | **Fable 5** | ユーザー自身が「Opus/Sonnet が理解できる文章で」と明示的に要求していた——つまり文書の**読み手**が別モデルになりうることを想定している。書き手を最上位モデルにすることで、曖昧さや暗黙の文脈依存を最小化できる。 |
| **反復サイクルをユーザーが手動で回している場合** | **`/loop` の使用を検討** | 本セッションは「続けて」を 20 回以上手動で送る形になった。同じパターンの反復だと判明した時点で `/loop`（間隔指定 or 自己ペース）に切り替えれば、同じ成果をユーザーの手を煩わせずに得られる。次に同種の連続改善サイクルに入ったら試す価値がある。 |
| **外部調査（Web 検索・ドキュメント参照）** | **Agent（Explore or general-purpose）** | メインの文脈を汚さずに済み、実際にこのセッションで機能した。モデル階層はタスクに応じて Sonnet 5 で十分（調査自体に高度な戦略判断は不要）。 |
| **変更後の独立検証**（「本当にこの主張は正しいか」を別の目で再確認） | **Agent（Explore, 読み取り専用）** | 本セッションで `FEATURE-AUDIT.md` の記載内容をスポットチェックする際に有効だった。自分で書いた内容を自分で検証すると見落としが残りやすいので、独立エージェントに投げるのが良い。 |

## 実務的な指針（次回以降のセッションで）

1. **迷ったら「指示が戦略的か実行的か」で選ぶ**——「何をすべきか」を問う指示なら
   Fable 5、「これをやって」と既に決まっている指示なら Sonnet 5、というこの
   セッションの実際のパターンを踏襲するのが最も実績がある。
2. **偽OK のリスクがある変更（検証ロジック・許容誤差・判定閾値に触れる変更）は
   Fable 5 を既定にする**。このプロジェクトの設計哲学（偽OK ≫ 偽BLOCK のコスト）と
   整合する。
3. **同じ改善サイクルを 3 回以上繰り返すと分かった時点で `/loop` を使う**。
   手動での「続けて」の連打は本質的に `/loop` の手動シミュレーションである。
4. **機械的な下調べ（スキャン・grep・ファイル読み取り）は Agent に投げてメイン
   文脈を汚さない**——本セッションで実際に有効だった数少ない Agent 活用例を
   踏襲する。
5. **Opus 4.8 は「Sonnet 5 では不安だが Fable 5 ほどの重さは不要」な中間層**——
   Fable 5 が「Opus 相当以上」ゆえ Fable 5 が使える限り最上位判断は Fable でよいが、
   設計判断を含む中規模ラウンド（torch 経路の段階接続・SP fork の一般化など）を
   コスト最適化しつつ任せる先として Opus を使う。具体的な担当割当は下記指示書を参照。

## モデル別指示書（会話履歴なしで作業開始できる）

改善バックログ（`docs/ASSESSMENT.md` の優先度表）を、モデルの得意領域に沿って
2 つの指示書に分けた。各指示書は「起動時に読む 3 ファイル」から始まり、台帳だけで
作業を開始できる（会話文脈に依存しない）。

- **`docs/INSTRUCTIONS-OPUS.md`** — 設計判断を含む中規模ラウンド（ASSESSMENT の P1:
  A-3 torch 経路接続・A-12 残の SP fork 一般化・A-2 実機ハーネス計画）。
- **`docs/INSTRUCTIONS-SONNET.md`** — スコープ確定済みの反復ラウンド（ASSESSMENT の P2:
  Q43/Q48・カバレッジ・ドキュメント同期）＋**エスカレーション基準**（偽OK リスクや
  曖昧判断に当たったら停止して Fable/Opus に委ねる）。
