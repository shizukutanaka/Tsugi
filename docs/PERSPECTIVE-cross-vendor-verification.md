# 視点の補完: クロスベンダー検証層（ソクラテス問答による発見）

> 2026-06-15。ソクラテス式問答で Tsugi 自身の前提を問うて発見した盲点。
> 「正しく作る（codegen）」に偏り、「移植が正しいと*証明する*」視点が欠落していた。

---

## 問答の記録

**Q1（前提検証）**: Tsugi は「痛み＝ベンダーロックイン脱却」と仮定。だが Triton は既に
torch.compile で NVIDIA+AMD を出す。なら Tsugi の存在理由は?
→ 差別化「行列コアレイアウト統一 autotuning」は*ユーザーの痛み*か*ビルダーの面白い問題*か?
Triton と正面競合する codegen はソロでは勝ち目が薄い。

**Q2（帰結）**: Triton が*やらない*ことは? → **両ベンダーが同じ数値を出す保証をしない。**
クロスベンダーの silent numerical divergence は実在の悪夢。リサーチ既出: AMD の弱点は
性能でなく「弱い QA 文化」（SemiAnalysis）。堀の本質はライブラリ＋**正しさの QA**。

**Q3（メタ）**: 「統一ドライバで CUDA 牙城を崩す」が正しい問いか? → 違うかもしれない。
最も価値があり・ソロで達成可能で・差別化できるのは**ドライバ/コンパイラ本体でなく、
クロスベンダー移植を*信頼できるものにする検証層*。しかもリファレンス oracle が既に中核資産。**

---

## 新視点（採用）

**Tsugi の最強の楔は codegen でなく「移植が正しいと証明する検証層」。**

2本柱:
1. **数値等価性（equivalence）**: リファレンス oracle を真値に、NVIDIA と AMD の実行結果が
   `max abs err < 1e-2 (FP16)` で一致するかを保証する（GPU 必要・既存ハーネスが土台）。
2. **移植性解析（portability）**: traced IR から*実行前に*移植リスクを静的に告げる
   （GPU 不要・`tsugi/portability.py` で実装済み・実行検証済み）。
   - warp(32) vs wavefront(64) の暗黙依存
   - 行列コア MMA 形状の非対応
   - bf16 行列コア対応のベンダー差

実例（実行確認済み）: 同一カーネル block=32 → NVIDIA は OK、AMD CDNA は WARN
（wavefront=64 の倍数でない）。**Triton はこれを告げない。**

---

## なぜこれが正しい楔か（視点の補完と接続）

- **アウトカム視点**: cuBLAS に勝つ必要がない。「移植が壊れない安心」という別の成果を売る。
- **ユーザー検証**: 「自分が欲しいから作る」が成立しやすい。クロスベンダー移植の不安は実在。
- **ソロ達成可能**: 19年のライブラリ蓄積に勝負しない。検証は静的解析＋oracle で作れる。
- **差別化**: Triton/IREE は codegen。等価性保証・移植前警告は空白地帯。

---

## 戦略への影響

- v0.1 のスコープに **portability 解析を正式機能として追加**（codegen と独立に価値を出す）。
- v0.1 は GPU 無しでも `tsugi.compile` + `portability.analyze` で「移植性レポート」を提供可能
  → **GPU codegen 完成を待たずに最初の実用価値が出る**（これが最大の収穫）。
- equivalence ハーネスは GPU 実機で稼働（既存 tests/correctness が土台）。

却下した代替視点:
- 「Intel/Apple を先に攻める」: 市場小・優先度低。却下。
- 「CUDA ソース移植ツール（HIPIFY 型）」: 既存解あり・差別化弱い。保留。

## 追補: 入力精度ポリシー差 — 最も一般的なクロス発散源（TF32）

クロスベンダー発散の源として、これまで equivalence 層は **累積順序差**（split-K・atomic）を
主に模してきた。だが実運用で最も一般的なのは **入力精度ポリシー差**である。

- NVIDIA Ampere+ は fp32 GEMM を既定で **TF32**（10 仮数 = fp32 の 23 から削減）に落としうる。
  PyTorch 2.9 で `torch.backends.cuda.matmul.fp32_precision = 'ieee' | 'tf32'` に移行し、
  `set_float32_matmul_precision('high'/'medium')` が tf32 に対応する。FlexAttention の既定精度が
  リリース間で ieee→tf32 に回帰した実例もある（同じコードでバージョンが変われば数値が変わる）。
- AMD ROCm は TF32 非対応。よって「fp32 の同一モデル」が NVIDIA(TF32) と AMD(IEEE) で
  ~2⁻¹¹ 相対だけ食い違う。これは *バグでなく既知の精度ポリシー差* である。

### 二種類の発散は質的に違う（本ラウンドの発見）

| 発散源 | K 依存性 | 機構 |
|---|---|---|
| 累積順序差（split-K・atomic） | **√K·u** で増える | 各累積ステップの丸めが random-walk で蓄積 |
| 入力精度差（TF32/bf16） | **K 非依存 ~u** | 入力仮数の丸めは各要素の *相対* 摂動で、和で相対量は変わらない |

数値実験で TF32 入力精度発散が K=256/2048/8192 いずれも相対 ~2.9e-4 と一定であることを確認した。
大 K では √K·u の累積が支配するため、`dtype="tf32"` の許容（√K·u）は入力精度発散を保守的に覆う。

### 診断: バグと精度ポリシー差を取り違えない

LAYOUT 判定（値の多重集合が一致 → 転置バグ）と同じ発想で、`precision_policy_hint` は fp32 系の
発散が「fp32 累積では説明できないが TF32 入力精度の範囲内」なら **バグでなく精度ポリシー差の
兆候** として拾い、`audit_runtime` で「fp32_precision='ieee' でピンするか dtype='tf32' 許容を
使え」と助言する。移植検証の価値は「発散を見つける」ことだけでなく「発散の *正体* を告げる」
ことにある——チームが phantom bug を追わずに済む。一次資料は Fasi/Higham/Mikaitis/Pranesh
（PeerJ CS 7:e330, 2021）・docs/SOURCES.md「入力精度（TF32/bf16）のクロス発散モデル」節。
