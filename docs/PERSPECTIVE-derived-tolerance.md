# 視点の補完 2: 導出される許容誤差（ソクラテス問答・第2ラウンド）

> 2026-06-15。直近で自分が作った equivalence の前提を問うて発見した盲点。
> 固定許容（1e-2）は恣意的だった。

---

## 問答の記録

**Q1（前提検証）**: equivalence は「NumPy f32 = 真値、AMD が ±1e-2 で一致するか」を問う。
だが NumPy f32 は本当に真値か? cuBLAS と rocBLAS は累積順序が違うだけで*両方 IEEE 正当*。
どちらも"間違い"でない。
→ 「基準に一致するか」の枠組み自体が歪み。両者は正当に異なる。

**Q2（帰結）**: なら何と比べる? → **数学が許す範囲**。matmul の誤差は累積深さ K・dtype の
機械イプシロンで決まる。well-conditioned な大K GEMM は*正当に*大きくズレる。固定 1e-2 は
大K を過剰検出し、小K のズレを見逃す。
→ 実証: K=2048 で固定 1e-2 が正当な f32 順序差を DIVERGENT と誤判定。導出許容
（√K·u_fp16·safety）では K=2048 → atol 8.8e-2 が数学的に正当な発散幅。

**Q3（メタ）**: 「閾値」を固定値で持つのが間違いでは? → **閾値は導出すべき**。
(1) 演算の数値条件（K・dtype・スケール）から期待誤差を計算、(2) HW 非決定性ノイズフロアと
比較。「魔法の数字に一致」でなく「数学が許す以上にズレない」へ。

---

## 新視点（採用）

**許容誤差は固定でなく演算条件から導出する。** `tsugi.tolerance`:
- `expected_gemm_abs_error(K, dtype, scale)` = safety·√K·u·scale
- `derive_tolerance(...)` = max(導出値, ノイズフロア) を {atol, rtol} で返す
- `equivalence.compare_gemm(a, b, K, dtype)` が導出許容で判定

実証（K 依存・実行確認済み）:

| K | 導出 atol (fp16) |
|---|------------------|
| 64 | 1.6e-2 |
| 512 | 4.4e-2 |
| 2048 | 8.8e-2 |
| 8192 | 1.8e-1 |

固定 1e-2 と異なり K に応じて変化。正当な f32 順序差は等価と判定（過剰検出しない）、
真の発散（f16 累積）は依然検出（検出器は鈍らない）。

---

## なぜ重要か

- **正しさの定義を正す**: 「ベンダーが基準に一致」でなく「数学が許す範囲に収まる」。
  両ベンダーは正当に異なる、という事実に整合。
- **過剰検出を防ぐ**: 固定閾値の偽陽性（大K GEMM を誤って DIVERGENT 判定）を解消。
- **誠実**: モデルは厳密な最悪ケース境界でなくランダムウォーク近似（明記）。
  safety 係数で粗さを吸収。HW ノイズフロア実測があればそれと合成。

## 設計への影響

- equivalence は固定（`compare`）と導出（`compare_gemm`）の両方を提供。
  GEMM は導出を推奨、汎用 op は固定 dtype 別。
- 実 GPU フェーズ: 各ベンダーの run-to-run 非決定性を実測 → noise_floor に投入し、
  「導出誤差 vs ノイズフロア」の大きい方を許容にする（さらに原理的に）。
